01 · Purpose

Executive summary

FOSIS sits at the centre of the school's student information landscape. It exposes canonical, versioned APIs and events to approved systems, and reads external data through explicit, mapped contracts. Each connection identifies the owner of each data domain, the permitted direction of flow, and the workflow that governs changes.

Architecture anchor. FOSIS is authoritative for student identity, guardian relationships, enrolment, academic structure, timetable, attendance, reports, and its own approved student-care records. External systems keep authority over their own domains—such as HR employment, CRM prospect pipeline, finance ledger, LMS content, exam-board results at source, and library circulation.

The integration plane comprises a public/API gateway, an internal connector and mapping layer, event outbox/dispatch, an identity and policy boundary, secret management, audit, health and reconciliation. First-party Backpack integrations use direct, purpose-specific FOSIS APIs and events. Third-party marketplace applications use a separate Epic 33 gateway. AI calls use a separate policy gateway and model adapter layer.

This is a reference architecture, not a claim that every connector or route already exists. Example API paths, scopes, event names, protocols, and service boundaries are proposals for Epic 24 (Integrations & API Platform), aligned with Epic 25 (Identity, RBAC & Delegated Permissions), Epic 26 (Audit, Compliance & Data Governance), Epic 33 (Marketplace), and Epic 40 (Library).

Direction legend. “FOSIS reads” means data enters FOSIS after source, tenant, schema, and permission checks. “FOSIS sends” means a consumer receives a filtered FOSIS projection or event. An external request that changes data is a command into a FOSIS workflow, never a direct database update.
02 · Context

Architecture at a glance

Read into FOSIS = teal. FOSIS publication or service = blue. Two-way connections are separately authorised in each direction. All boxes are logical system families, not vendor selections.

Trust zones

  • FOSIS core: system of record, domain services, deterministic rules, approval workflows, authoritative audit.
  • First-party experience: Friends of School/Backpack uses canonical APIs and events, with minimum necessary parent-facing data.
  • External school systems: direct or adapter-based integration with a field-level source-of-truth map and per-school connection configuration.
  • Marketplace vendors: third-party connections isolated behind a separate gateway and installation lifecycle.
  • AI providers: separate inference boundary; models receive only approved task context and return constrained drafts/recommendations.
  • Analytics: downstream read model or extracts; never a direct write path to the transactional database.
03 · Design rules

Principles and boundaries

  1. API-first; no direct database access. Systems exchange versioned contracts over TLS. No partner, plugin, AI provider, or reporting tool receives database credentials or general query access.
  2. Field-level ownership. Each data field has an authoritative owner, a permitted direction, a conflict policy, and provenance. “Last write wins” is not a safe default for student records.
  3. Least privilege and tenant isolation. Tenant context is derived from an authenticated credential and verified on every request; IDs alone never grant access.
  4. Events for change notification; APIs for current detail. Events are minimal signals. Consumers fetch a permitted current view after their own entitlement is rechecked.
  5. Commands enter workflows. Parent, vendor, CRM, and partner write-backs use named commands or requests with validation, idempotency, authorisation, and human approval where policy requires it.
  6. Minimise replicated records. Publish projections needed for one purpose. Do not create a second student master in Backpack, a plugin, AI provider, or warehouse.
  7. Reversible operations. Imports have dry-run, validation, reconciliation, and rollback plans where technically safe. Connections can be suspended and credentials revoked without deleting authoritative history.
  8. AI assists; it does not authoritatively act. Business rules, access checks, and human decision-makers remain in control.

Data classes used by the gateway

Operational Personal Sensitive Restricted

Every API and event schema carries a data classification. A school connection is approved for a tenant, system purpose, field set, event list, retention period, and data class. Sensitive health or learning-support data and restricted safeguarding material are denied to general-purpose integrations by default.

Inbound data path

  1. Authenticate provider, verify tenant and configured connection, then enforce scope and allowed source network/certificate as applicable.
  2. Validate signature or OAuth token, request size, schema version, idempotency key, timestamp, and replay window.
  3. Map provider identifiers to immutable FOSIS IDs; normalise dates, codes, time zones, locale, and status values.
  4. Apply deterministic business rules and field ownership. Reject or quarantine conflicts; do not make a silent merge.
  5. Write via a domain command with actor/connection provenance and audit. Emit downstream events only after transaction commit.
  6. Return a correlation/reference and business outcome. Reconcile failures using an operator-visible queue.

06 · Connections

System connection catalogue

Each card distinguishes inbound reads, outbound delivery, ownership, and controls. A school enables only the connections it uses. “Possible” means supported by the architecture pattern; the exact connector, provider, regional rules, and data contract are selected and validated per school.

CONNECTION PATTERN

1. Staff identity provider and school directory

Authentication is federated; authorisation remains in FOSIS.

FOSIS reads

FOSIS consumes SAML 2.0 or OIDC login assertions, stable staff identifiers, and optional group claims. Provisioning may use SCIM or a controlled staff-directory feed where supported.

FOSIS sends

FOSIS returns the minimum identity and session claims needed by the staff application. It maps a verified external identity to a FOSIS person, tenant, role, and contextual permissions.

Authority

The identity provider owns credentials and authentication. FOSIS owns tenant membership, role assignment, student/group scope, delegated access, and application authorisation.

Boundary and control

Require verified issuer/audience, signed assertions, short-lived sessions, MFA for privileged actions, deprovisioning, and deny-by-default role mapping. A successful SSO login does not itself grant access to student records.

CONNECTION PATTERN

2. School HRIS and payroll

Inbound staff feed with narrowly controlled operational feedback.

FOSIS reads

FOSIS reads staff identifier, preferred name, work contact, employment state, start/end dates, department, and approved role or qualification attributes needed for teaching, timetabling, and access provisioning.

FOSIS sends

FOSIS may return teaching assignments, timetable duties, or a staff-access deactivation notice where the HR contract explicitly permits it. Payroll, salary, bank, tax, and benefits data are out of scope.

Authority

HR owns employment facts and payroll. FOSIS owns teaching/group assignments and the effective-dated SIS permissions it administers.

Boundary and control

Map on immutable staff IDs; reject ambiguous identities into a reconciliation queue. HR termination can disable access promptly, while preserving historic teaching and audit records.

CONNECTION PATTERN

3. CRM, admissions CRM, and applicant systems

Prospect-to-student handoff, with ownership changing at an explicit lifecycle boundary.

FOSIS reads

FOSIS can ingest an accepted applicant, guardian links, application identifiers, offer status, and required enrolment evidence from the school CRM or admissions platform.

FOSIS sends

FOSIS can return a minimal admission/enrolment outcome, canonical student reference, and completion status so the CRM can close or continue its own workflow.

Authority

The CRM owns prospecting and sales/admissions pipeline. FOSIS becomes authoritative for canonical student identity, guardian relationships, enrolment, academic placement, and the school record after conversion.

Boundary and control

Use explicit conversion commands, source-system IDs, duplicate warnings, and non-destructive field mappings. Never infer guardian/student relationships from matching names or email addresses alone.

CONNECTION PATTERN

4. Legacy SIS, district platforms, and migration sources

Migration and cutover feeds; not an indefinite dual-master arrangement.

FOSIS reads

FOSIS imports students, guardians, staff, academic structure, enrolments, timetables, and permitted history through versioned CSV/API contracts, dry-runs, validation reports, and reconciliation.

FOSIS sends

During transition, FOSIS can publish validated reconciliation extracts and cutover acknowledgements to authorised migration teams or the legacy system.

Authority

The designated source SIS remains authoritative until an agreed cutover. After cutover, FOSIS is the system of record for the migrated student journey.

Boundary and control

Preserve source identifiers and provenance, distinguish rejected rows from warnings, use repeatable imports, and require a signed-off cutover and rollback plan.

CONNECTION PATTERN

5. Learning management systems (LMS)

Roster and teaching context outward; optional learning evidence inward.

FOSIS reads

Where the school requests it, FOSIS may read completion, assignment, or assessment evidence from an LMS for review or a permitted learning workflow.

FOSIS sends

FOSIS supplies current student/teacher identifiers, class and teaching-group rosters, subject/course codes, academic dates, and membership changes to the LMS.

Authority

FOSIS owns official identity, enrolment, class membership, timetable context, and any official grade/report record held in the SIS. The LMS owns its course content and learning activity. Imported evidence must not silently overwrite official grades.

Boundary and control

Use immutable IDs and standards-based mappings such as OneRoster where both endpoints support the same profile. Scope by tenant, course, and academic period; send withdrawal and membership-removal events.

CONNECTION PATTERN

6. Examination boards and assessment providers

Candidate entry outbound; result and qualification data inbound.

FOSIS reads

FOSIS imports candidate identifiers, subject entries, result codes, grades, and qualification outcomes returned by an authorised examination provider.

FOSIS sends

FOSIS publishes validated candidate entries, subject codes, access arrangements only where explicitly permitted, and required school references.

Authority

FOSIS owns the student record and school-entered internal grades; the examination provider owns the examination outcome at source. Imported outcomes retain provider, series, and timestamp provenance.

Boundary and control

Validate candidate matching, exam series, and code lists. Quarantine mismatches and require authorised review before results are published to students or parents.

CONNECTION PATTERN

7. Finance, fees, ERP, and payment providers

Operational fee references and payment state; no general-ledger replacement.

FOSIS reads

FOSIS may receive payment status, invoice references, fee-plan status, refunds, and reconciliation outcomes from the school finance or payment service.

FOSIS sends

FOSIS may send student/enrolment references, chargeable activity references, approved fee schedules, and payment request metadata. Payment callbacks return through signed webhooks.

Authority

The finance/ERP owns ledger entries, settlement, tax, refunds, and account balances. FOSIS owns the student/enrolment and school workflow that triggered a charge, plus only the payment status needed by that workflow.

Boundary and control

Do not store payment-card data in FOSIS. Verify callback signatures, use idempotency keys, reconcile against provider references, and require a human-approved policy before fee state can block an enrolment action.

CONNECTION PATTERN

8. Government, regulator, and statutory systems

Jurisdiction-specific data submission and reference-data intake.

FOSIS reads

FOSIS can ingest official code lists, school identifiers, validation errors, acknowledgement receipts, and permitted reference data from government services.

FOSIS sends

FOSIS can produce required enrolment, attendance, attainment, census, and statutory returns, using school- and jurisdiction-approved mappings.

Authority

FOSIS owns the originating student and school facts. The authority owns its identifiers, receipt, and statutory decisions. The integration must not convert a regulator response into an unreviewed student-record change.

Boundary and control

Version schemas by jurisdiction and reporting period; minimise fields, apply export approvals, encrypt transfers, retain submission receipts, and log who approved each disclosure.

CONNECTION PATTERN

9. Transport, facilities, and room/resource systems

Eligibility and scheduling context exchanged with an operational provider.

FOSIS reads

FOSIS may read route allocation, stop/route reference, service eligibility, room availability, closures, and confirmed external resource bookings where these systems own the operational inventory.

FOSIS sends

FOSIS publishes only the student eligibility and timetable/resource requests required to run the service, plus approved room bookings or timetable occupancy.

Authority

FOSIS owns student enrolment, timetable intent, and its own room/facility records. Transport providers own vehicles, drivers, routes, live tracking, and operational journeys; a facilities platform may own its local availability calendar.

Boundary and control

Do not disclose live student location or route membership beyond the permitted provider and purpose. Use effective dates, guardian permissions where required, and rapid access removal on withdrawal.

CONNECTION PATTERN

10. Friends of School / Backpack (first-party)

Default parent-facing experience using canonical APIs and events.

FOSIS reads

Backpack reads minimal, purpose-specific views such as the selected child’s timetable, attendance, published reports, consent actions, action list, and library due/overdue summary where authorised.

FOSIS sends

Backpack submits profile-change requests, document uploads, consent responses, leave/absence requests, and other approved parent intents. These become FOSIS workflow requests, not direct record updates.

Authority

FOSIS is authoritative for the SIS record and guardian-student relationship. Backpack owns messaging UX and its own community/shop content. FOSIS supplies identity/relationship context; Backpack does not create a shadow SIS.

Boundary and control

Use scoped REST APIs and events, immutable IDs, no general database access, and no continuous polling. Do not replicate medical, safeguarding, SEND, or full academic histories; expose only specifically permitted views.

CONNECTION PATTERN

11. Email, SMS, and notification delivery services

Outbound channel delivery with status callbacks; multiple channels are configurable.

FOSIS reads

FOSIS receives delivery, bounce, opt-out, and provider message-status callbacks, matched to its own notification and recipient IDs.

FOSIS sends

FOSIS or the selected first-party messaging service sends approved notification templates to configured one or more channels, including Backpack, email, or SMS.

Authority

FOSIS owns the trigger, recipient eligibility, channel configuration, and communication audit. A delivery provider owns transport status only.

Boundary and control

Record each channel attempt and outcome separately, apply consent and contact restrictions, use template version IDs, and avoid sending sensitive incident detail in an insecure channel.

CONNECTION PATTERN

12. Library service (Epic 40)

Separate, integration-first service; FOSIS supplies identity, tenancy, and permissions.

FOSIS reads

FOSIS can query a permitted, student-scoped summary of loans, due dates, and overdue status. Backpack can display that summary to the linked guardian/student under FOSIS permissions.

FOSIS sends

FOSIS supplies an opaque immutable person/student reference, tenant, active status, and minimum identity needed for matching and access. It can pass role/permission assertions to the library service.

Authority

The separately deployed library product owns catalogue, copies, circulation, returns, reservations, and fines. FOSIS does not become a library catalogue or circulation system.

Boundary and control

Select and review a suitable MIT/Apache-licensed service before adoption. Keep the service separately deployed; use API contracts, tenant-aware identity, no shared database tables, and a revocable service credential.

CONNECTION PATTERN

13. Marketplace vendors and plugins (Epic 33)

Third-party access through a separate, controlled marketplace gateway.

FOSIS reads

An installed vendor receives only the school-approved data scopes and event subscriptions named at installation, such as roster read or a specific attendance workflow.

FOSIS sends

A vendor can return a named command or result through an approved API; FOSIS validates tenant, scope, schema, idempotency, and workflow authority before accepting it.

Authority

The vendor owns its service and its declared processing; FOSIS remains authoritative for FOSIS data. Friends of School/Backpack is first-party and does not go through third-party vendor treatment.

Boundary and control

Require vendor review, school installation, explicit scopes, two-authorised-person approval for each install/update, paid-item finance rules, credential vaulting, audit, contract/data review, health monitoring, and immediate disconnect/revocation. Never grant raw database or general FOSIS access.

CONNECTION PATTERN

14. AI models, document AI, and inference services

Model-neutral inference behind a privacy and policy gateway.

FOSIS reads

FOSIS submits only task-authorised minimum context to an allow-listed provider/model. The gateway can redact or pseudonymise identifiers, enforce tenant boundaries, choose a model, and reject prohibited data classes.

FOSIS sends

The model returns a constrained draft, classification, extraction, translation, or recommendation. FOSIS validates schema and policy, records model/prompt/schema metadata, and presents eligible output to an authorised human.

Authority

FOSIS owns all authoritative records and deterministic rules. The AI provider is a processor for the configured task. No provider response directly changes an authoritative record or makes a material school decision.

Boundary and control

Use configurable provider adapters, model allow-lists, retention/region review, minimum necessary context, output validation, rate/cost limits, prompt-injection defences, and human approval. Safeguarding, medical, and SEND content are excluded by default unless an explicit approved policy says otherwise.

CONNECTION PATTERN

15. Analytics warehouse, reporting, and data export

Read-only downstream projection, separated from the transactional database.

FOSIS reads

FOSIS exports approved facts through a tenant-aware warehouse feed, event stream, or scheduled extract. Consumers query a curated reporting model, not the OLTP database.

FOSIS sends

The warehouse or BI tool returns aggregate results, validation findings, and report outputs to authorised school users; it does not write student facts back through a database connection.

Authority

FOSIS owns source facts and change history. The warehouse owns derived models and aggregate outputs with lineage to source versions.

Boundary and control

Apply column/row-level scopes, de-identify where possible, restrict sensitive domains, log exports, document retention, and prevent cross-tenant joins.

07 · Contracts

Canonical API and event patterns

API conventions

  • REST/JSON canonical resources under versioned paths such as /v1; use major-version compatibility rules and publish schemas and deprecation windows.
  • Tenant is derived from signed credentials/claims and connection installation, not trusted from a caller-supplied body field.
  • Use OAuth 2.0 scoped tokens for machine-to-machine access; use OIDC or SAML federation for interactive school sign-in. Use short-lived tokens and rotate secrets.
  • Read paths are purpose-specific and filter fields by both scope and user/relationship context. Use cursors for bounded reconciliation; avoid broad scheduled polling where events meet freshness needs.
  • Writes are named commands/requests, with validation, idempotency key, actor, reason, optional approval and a returned workflow state. Do not expose generic PATCH/SQL-like update functions to integrations.
  • Use stable opaque IDs plus external-ID mapping tables. Never depend on email or display name as a join key.
  • Standardise pagination, UTC timestamps plus explicit school timezone, error shape, retry-after, correlation IDs, and rate-limit headers.

08 · AI

AI model integrations

AI models connect through an AI-specific policy gateway, not as ordinary marketplace plugins. The gateway isolates providers and makes model routing changeable without changing FOSIS domain services.

Provider and model flexibility

Define a provider-neutral adapter contract for hosted model APIs and, if separately approved, private or school-managed inference endpoints. Each connection is configured with allowed tasks, model identifiers, region, data-retention terms, token limits, timeouts, retries and cost budgets. The selected provider must pass contractual, technical and jurisdiction review; no brand is assumed to be approved by this document.

Default deny for restricted records. Do not send safeguarding chronology, medical records, or SEND/learning-support documents to a model unless a school-approved task-specific policy explicitly authorises the data class and provider. No AI response may independently diagnose, decide safeguarding severity, alter enrolment, select a school outcome, or publish a report.

For personally identifiable content, use provider retention controls only when enabled and contractually confirmed for the organisation/project. Zero-data-retention eligibility, where available, is a reviewed control—not a promise that data never leaves FOSIS. Batch routes and provider features must be checked individually because retention guarantees may differ.

09 · Marketplace

Marketplace and plugin interaction

Epic 33 is a separate vendor control plane and gateway. It does not dilute Epic 24’s general API platform or turn FOSIS into an open data lake. The school chooses a listing, installs it for its tenant, grants named scopes, and can revoke it at any time.

  1. Vendor registration: identity, company, service purpose, regions, subprocessors, support contact, security posture, data retention, and permitted product category.
  2. Review and listing: product/security/privacy review, API contract and scopes, vulnerability process, service status, and commercial terms. Paid plugins follow school finance rules, including subscription, refund, and revenue-share accounting where applicable.
  3. School installation: an authorised school administrator selects tenant, purpose, events, fields and actions. A second authorised person approves each installation and each scope/update change.
  4. Credential issuance: gateway issues a dedicated, revocable client credential with tenant-bound scopes and expiry/rotation policy. No shared school-wide secret or direct database credential.
  5. Run and monitor: API/event traffic is rate limited, validated, audited and health checked. Errors are visible and retried safely; repeated unsafe behaviour can suspend a connection.
  6. Update: new permissions or data use require a fresh review and two-person approval. Existing consent/scope is not silently broadened.
  7. Disconnect: revoke token and signing key, stop event delivery, disable callbacks, close commercial subscription, record the action and preserve required audit evidence.

11 · Operations

Reliability and operations

  • Delivery semantics: API calls may be synchronous for bounded requests; event delivery is at-least-once with consumer deduplication. Exactly-once delivery is not assumed.
  • Retries: bounded exponential backoff with jitter for timeouts and transient 5xx/rate limits; respect Retry-After. Do not retry invalid schema, authorization, or business-rule failures indefinitely.
  • Queues: use a dead-letter/quarantine queue, replay controls, event age monitoring, and per-tenant backlog view. Replays are audited and keep the original event ID plus replay metadata.
  • Idempotency: require an idempotency key for write commands and payment callbacks; define deduplication window and durable key storage.
  • Observability: monitor API success/latency, event delivery delay, provider health, mapping failures, invalid tokens, backlog size, rate-limit rejections, and per-tenant volume. Logs mask PII.
  • Reconciliation: schedule source-to-FOSIS counts or checksums for critical feeds; show missing, duplicate, conflicting and stale records. Reconciliation does not auto-correct authoritative values without policy.
  • Resilience: circuit breakers for unhealthy providers; local queues for noncritical outbound notifications; controlled manual export/import path for approved outage recovery.
  • Isolation: per-tenant quotas and fair scheduling protect smaller schools from noisy neighbours. Keep connector jobs from competing with registration, timetable and student lookup paths.

Connection owner and status · last successful call/event · freshness and backlog · failure categories · last schema/mapping version · scopes and expiry · credential rotation date · tenant and school · pending approval/reconciliation queue · disconnect and replay controls · audit link.

13 · Follow-on specifications

Decisions and next specifications

Architecture decisions set in this reference

  • FOSIS remains the authoritative SIS for the student journey; external systems retain authority in their domains.
  • API-first, versioned REST plus event/webhook patterns; no direct third-party or analytics database access.
  • First-party Backpack integration is separate from third-party marketplace installations.
  • Epic 33 vendors use a separate gateway, school-approved scopes, credential lifecycle, audit, review, and disconnect; a second authorised person approves installation and updates.
  • AI uses a separate policy gateway, provider-neutral adapters, minimal context, validation, and human approval before authoritative action.
  • Epic 40 library remains a separately deployed service; FOSIS supplies identity, tenancy, permissions and APIs; the library owns circulation.
  • Student, medical, safeguarding, and learning-support data are not generally exposed to plugins or AI by default.

To define in API specifications

  • Canonical API schemas and formal OpenAPI documents; event envelope and schema registry.

  • Rate limits, service objectives, token expiry/rotation, webhook signature scheme, and per-tenant throughput limits.
  • Standards profiles adopted per provider (for example OneRoster where supported) and country-specific regulator connectors.
  • Operational runbooks, migration cutover plan, incident process, customer support and vendor exit data handling.
